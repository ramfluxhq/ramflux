# Ordinary DM bootstrap forward secrecy

Ordinary direct-message bootstrap uses the device's stable X25519 identity key, a rotating signed
prekey, and, when available, one one-time prekey (OPK). Signed-prekey and OPK private keys are
generated by the operating-system CSPRNG. A published bundle contains the stable public identity,
the current signed-prekey public key, its creation and expiry times, and a pool of individually
signed OPK public keys. No private prekey is published.

## Rotation and directory consumption

- A signed prekey is valid for 30 days and devices rotate it after seven days when online. This
  keeps an offline device reachable during the signed validity window. A bundle older than 30 days
  is rejected with a refresh-required error. The previous private signed prekey is retained for a
  two-day delivery grace and is then erased, including when read. At most one current and one grace
  key are retained.
- Each device publishes eight OPKs. Publish and sync responses report the directory's remaining
  unleased count; when that count falls below two, the device generates and publishes a completely
  fresh pool with fresh identifiers. The directory accepts at most 32 OPKs in one bundle. Reaching
  zero also records a typed `x3dh.one_time_prekeys.exhausted.v1` owner warning.
- Bundle counters increase monotonically. Republishing the same bundle is idempotent and does not
  replenish directory OPKs; older counters are refused.
- An authenticated account session may lease one OPK for a root-qualified device. The gateway
  forwards the verified fetcher principal and the real masked source prefix to the router. The
  directory atomically removes exactly one OPK and returns only its identifier, public key, and
  individual signature alongside the SPK. Concurrent fetches cannot receive the same OPK, and a
  receiver cannot substitute another pooled OPK. A consumed identifier is never restored by
  restart or idempotent publication.
- Anonymous fetches return an SPK-only bundle and never lease an OPK. In-memory hourly limits are
  independent per fetcher principal, per fetcher-target pair (three), and per source prefix, so one
  fetcher cannot drain a target or consume another fetcher's allowance. Durable lease progress is
  written incrementally per target device before the response; rate counters are not persisted.
- When the queue is empty, the directory returns the signed-prekey-only bundle and increments a
  bounded exhaustion counter with a rate-limited warning. All availability and rate-limit maps
  have hard account/source caps.

## Erasure and migration

The receiver erases an OPK private key in the same account transaction that commits the first
authenticated ratchet state derived from it. Initial X3DH outputs and transient key objects are
zeroized on drop. The initiator's first ratchet key is freshly generated and is distinct from the
X3DH ephemeral, whose private bytes are erased immediately after shared-secret derivation;
persisted ratchet snapshots cannot reproduce the bootstrap secret. Persisted snapshots contain
only the advanced ratchet state. Expired
signed-prekey private keys are erased during startup/publication maintenance after the delivery
grace. Existing ratchet sessions are unchanged.

The account database enables SQLite secure deletion. On both routed and legacy receive paths, the
authenticated ratchet snapshot and OPK removal commit in one transaction; only after it commits is
the pending in-memory consumption marker cleared, followed by a `TRUNCATE` WAL checkpoint. Private
state serialization and load buffers, and the decoded private-key state itself, are zeroized on
drop.

New private prekey state is device-local and is never copied to another device or backup. Existing
seed-derived bundles are replaced by a fresh CSPRNG bundle on the next publication. Legacy private
prekey event payloads and their projection pointers are retired with secure deletion before the new
state is selected.

Every possible storage copy is handled explicitly:

| Copy | Treatment |
|---|---|
| Device-local identity store | Current SPK, grace SPK, and unused OPKs only; consumed/expired keys are removed atomically. |
| DM session store | Only advanced double-ratchet snapshots are persisted; no SPK, OPK, or X3DH root input is stored. |
| Local legacy event log | `x3dh.prekey.private` payloads and signatures are overwritten with retired tombstones. |
| Encrypted backup snapshot | Device-local private-prekey actor state is deleted and legacy events are retired before the snapshot is finalized. |
| Backup archive tables | Private-prekey actor rows are excluded and archived legacy event payloads are retired during merge. |
| Own-device history/sync bundles | Private-prekey events and their checkpoints are excluded; private actor state is outside the exported history surface. |
| Directory/router store | Public keys, availability identifiers, counters, and rate-limit metadata only; never private key material. |
| Logs and metrics | Identifiers, counts, and exhaustion totals only; no private or public key bytes. |

## Threat statement

After an OPK-backed bootstrap is committed, later compromise of the device seed, live account
database, backups, directory state, and current prekeys cannot reconstruct the captured bootstrap
packet. Signed-prekey-only fallback has forward secrecy after that signed prekey's rotation grace
ends. This does not protect a device compromised before erasure, endpoint plaintext, or an active
attacker controlling the unlocked process. Existing replay-window and bootstrap-ordering checks are
unchanged.

As in Signal-style prekey systems, a malicious directory can strip an available OPK and force the
signed-prekey-only fallback. Signed bundle verification detects substitution but cannot prove that
the directory withheld a key. Authenticated leasing, exhaustion telemetry, and owner warnings make
drain and withholding observable; they do not provide cryptographic prevention of this downgrade.

The bootstrap transcript is unambiguous: every variable-length field is length-prefixed and binds
both root-qualified identity keys, device identifiers, the X3DH ephemeral, the selected OPK (or its
explicit absence), the bundle hash, and the initiator's fresh ratchet public key.
